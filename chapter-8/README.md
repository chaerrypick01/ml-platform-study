# Chapter 8 — 객체 탐지 모델 학습과 검증

준비한 데이터로 YOLO 모델을 학습하고, 가중치를 별도 검증 단계로 넘기는 과정을 다룬다. 이번 장에서는 작은 YOLOv8n 모델을 사용해 7장의 COCO128 분할을 이어받는다.

## 시작하기

이 장의 환경과 실행 명령은 [RUNBOOK](RUNBOOK.md), 결과는 [RESULTS](RESULTS.md)에 정리했다. `chapter-8/.venv`와 `chapter-8/requirements.txt`를 사용한다.

## 실습 범위와 목표

스터디 8.1의 흐름은 커스텀 데이터 설정 → 학습 컴포넌트 → 검증 컴포넌트 → KFP 실행 → 저장 가중치로 추론 확인이다. 이 저장소에서는 7장의 COCO128과 YOLOv8n을 연결한다.

- 기본 가중치와 1·5·10 epoch 가중치를 동일한 조건에서 비교한다.
- 탐지 지표와 예측 이미지로 학습 결과를 해석한다.
- Mac CPU/MPS의 학습 시간과 Linux Pod에서의 파이프라인 실행을 각각 확인한다.


목표는 **준비된 데이터를 학습에 사용하고, 저장한 가중치를 다시 읽어 같은 기준으로 비교할 수 있는 실험을 만드는 것**이다. 학습 명령이 끝났다는 사실과 모델이 좋아졌다는 판단을 구분한다. 전자는 실행 상태와 산출물로, 후자는 동일한 validation 데이터의 지표로 확인한다.

| 실습 | 입력 → 수행 작업 → 출력 | 확인하려는 것 |
|---|---|---|
| 로컬 학습 | 준비된 COCO128과 `yolov8n.pt` → 학습·validation 평가 → 가중치, 지표, 이벤트 로그 | 저장한 모델을 다시 읽어 평가할 수 있는지 |
| 체크포인트 비교 | 기본 가중치와 1·5·10 epoch 가중치 → 동일한 validation 평가·선택 → 선택 결과와 test 지표 | 학습이 진행되면서 탐지 성능이 어떻게 달라지는지 |
| CPU/MPS 측정 | 같은 데이터·초기 가중치·설정 → 각 장치에서 3 epoch 학습 → 전체 시간과 epoch별 시간 | 이 실습 규모에서 장치별 실행 비용이 어떻게 다른지 |
| KFP 실행 | 준비 Pod → Dataset → 학습 Pod → Model → 검증 Pod | 파일이 Pod 경계를 넘어 전달되고 별도 단계에서 모델을 평가할 수 있는지 |

로컬 비교 실험과 KFP 실행은 별개다. 현재 KFP 파이프라인은 하나의 epoch 설정으로 학습·검증하며, 1·5·10 epoch 비교와 CPU/MPS 측정을 자동으로 수행하지 않는다. KFP는 작업 실행과 입출력 연결을 담당하고, 학습·평가 자체는 각 컴포넌트가 호출하는 YOLO 코드가 수행한다.

## 데이터 준비와 모델 검증의 연결

YOLO 데이터 YAML에는 이미지 루트, 학습·검증 경로, 클래스 이름을 기록한다. 라벨 한 줄은 클래스 ID와 정규화한 중심 좌표·너비·높이다. 학습 컴포넌트는 이 설정을 읽고 가중치를 만들며, 검증 컴포넌트는 저장된 가중치를 다시 로드해 같은 validation 분할에 적용한다.

KFP YAML을 컴파일하는 것은 실행할 작업을 정의하는 단계다. 실제 학습이 성공했는지는 Run 상태, Pod 로그, 체크포인트, 검증 지표로 확인해야 한다. OpenCV 등의 시스템 라이브러리가 필요하므로 이번 실습은 의존성을 설치한 컨테이너 이미지를 사용한다.

### 어떤 입력과 출력이 필요한가

로컬 `--dataset`에는 [7장의 데이터 준비 기준](../chapter-7/README.md)에 맞는 디렉터리를 전달한다. `images/{train,val,test}`, 같은 이름의 `labels/{train,val,test}`, `data.yaml`, `manifest.json`이 필요하다. 기본 분할은 96/16/16장이다. `--weights`는 학습을 시작할 `yolov8n.pt` 파일이고, `--output`은 이번 실행의 새 출력 디렉터리다. 학습·평가 함수는 실행 위치에 맞게 `data.yaml`의 루트 경로를 다시 설정한다.

7장의 출력 디렉터리를 재사용할 수 있지만, 8장만 실행할 때는 `prepare_data.py`로 데이터를 준비할 수도 있다. 현재 KFP의 `prepare_data`는 컨테이너 안에서 원본을 다시 다운로드한다. 로컬 데이터 경로를 클러스터로 자동 업로드하는 구현은 아니다.

| KFP 단계 | 입력 | 수행 작업과 출력 |
|---|---|---|
| `prepare_data` | seed, 공개 데이터 다운로드 URL | 검사·분할한 Dataset과 HTML QA 보고서, 이미지 개수 반환 |
| `fit_model` | Dataset, epoch 수, 이미지에 포함된 초기 가중치 | 학습과 내부 validation 평가 후 가중치·실행 기록을 Model 디렉터리에 저장 |
| `score_model` | 같은 Dataset과 전달받은 Model | `model.pt`를 다시 로드해 validation 평가, Metrics·혼동 행렬·HTML 보고서 생성 |

학습 출력의 `fit/weights/`에는 체크포인트가, `tensorboard/`에는 이벤트 로그가 남는다. `result.json`에는 시간·평가 결과가 기록되고 `eval/evaluation.json`에는 가중치 해시와 지표가 기록된다. 현재 `model.pt`는 **마지막 체크포인트인 `last.pt`를 복사한 파일**이며, `best.pt`를 선택한 결과가 아니다.

### 실습 완료 기준

- 로컬 학습은 저장한 가중치와 평가 JSON을 확인하고, 검증 과정에서 생성한 예측 이미지로 놓친 객체·잘못 탐지한 객체를 살펴본다.
- 비교 실험은 기본 가중치를 포함한 네 후보를 같은 validation 16장으로 평가한다. `experiments.py`는 validation mAP50-95가 가장 높은 후보를 고른 뒤 test 16장으로 한 번 평가하고 `summary.json`에 남긴다. test 결과로 후보를 다시 고르지 않는다.
- KFP 실습은 준비·학습·검증 작업의 성공과 출력 아티팩트를 함께 확인한다. YAML 컴파일 성공만으로 완료로 판단하지 않는다. 현재 KFP 검증 단계는 validation을 사용하며 test 평가·모델 선택은 로컬 비교 실험에 구현되어 있다.

성능이 기본 가중치보다 높아야만 실습에 성공한 것은 아니다. COCO128은 작은 연결 실습이고 사전 학습 데이터와 겹칠 가능성이 있다. 이 결과로 새 도메인의 일반화 성능이나 서비스 배포 준비가 검증됐다고 해석하지 않는다.

## 지표를 읽는 법

| 지표 | 의미 | 해석할 때 확인할 점 |
|---|---|---|
| Precision | 탐지한 객체 중 올바른 탐지의 비율 | 잘못 탐지하는 정도 |
| Recall | 실제 객체 중 찾아낸 비율 | 놓치는 정도 |
| mAP50 | IoU 0.5에서 클래스별 AP를 평균 | 박스 위치가 비교적 느슨하게 맞아도 인정 |
| mAP50-95 | IoU 0.5~0.95의 AP를 평균 | 더 정확한 박스 위치까지 요구 |
| 혼동 행렬 | 실제·예측 범주의 조합 | 객체 탐지에서는 background도 포함 |

학습 손실이 줄었다고 validation 성능이 반드시 좋아지지는 않는다. 학습에 사용하지 않은 동일한 분할과 같은 추론 조건으로 가중치를 비교해야 한다. `best.pt`는 검증 기준으로 선택한 체크포인트이고, `last.pt`는 마지막 학습 결과다. 1·5·10 epoch를 비교할 때는 해당 시점에 저장된 체크포인트를 사용한다.

## 도전 과제

1. 기본 가중치와 1·5·10 epoch 체크포인트를 같은 validation 16장으로 평가한다.
2. 학습률·배치·이미지 크기·seed를 고정하고 Mac 호스트의 CPU와 MPS 학습 시간을 비교한다.
3. KFP에서도 Dataset → 학습 → Model → 검증을 실제 Pod로 실행한다.

10 epoch 한 번의 학습에서 중간 체크포인트를 꺼내는 방식은 같은 학습 경로의 진행 상태를 비교한다. 총 epoch 수를 각각 1·5·10으로 설정한 독립 실험과는 학습률 스케줄 등이 달라질 수 있다.

MPS는 Mac 호스트에서 사용하는 PyTorch 백엔드다. Docker Desktop의 Linux kind Pod에서 MPS를 사용한 것으로 기록하지 않는다. GPU가 항상 더 빠르다고 가정하지 않고 첫 epoch와 이후 epoch 시간을 함께 관찰한다. 작은 데이터에서는 초기화·전송 비용의 영향이 크다.

구현은 [train.py](train.py), 비교 실험은 [experiments.py](experiments.py), 실행 명령은 [RUNBOOK](RUNBOOK.md)에 있다. 실행 수치는 로컬 `outputs/<실행 이름>/summary.json`에 저장된다.

## 실습 결과

[가중치 비교·CPU/MPS 측정 결과](RESULTS.md)를 참고한다. 새 3 epoch 측정에서 CPU 전체 시간은 14.80초, MPS는 18.63초였으며, 첫 epoch를 제외한 학습 시간 중앙값은 각각 3.84초와 2.98초였다. 전체 시간과 학습 callback 구간을 구분한다.
